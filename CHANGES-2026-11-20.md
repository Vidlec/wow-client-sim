## Night: the gamepad

WoW Forever has a whole gamepad interface (Blizzard_Gamepad, its action bars, smart navigation, targeting), loaded
with the game's own interface but never switched on in the simulator. Now (`lua/gamepad.lua`):

- **A controller** plugged in plays it: the page reads it through the browser's Gamepad API and sends its buttons by
  the client's key names (PAD1, PADDUP, PADLTRIGGER...) and its sticks as the game's Movement and Camera sticks.
  `C_GamePad` answers from it (the mapped state, button and stick names, the active device), with
  `GAME_PAD_CONNECTED` and `GAME_PAD_ACTIVE_CHANGED`.
- A button goes to frames taking gamepad buttons first (`EnableGamePadButton`, `OnGamePadButtonDown/Up`), then to the
  bindings: the override bindings (the game's menus set them), the gamepad mode's binding context while active
  (`C_KeyBindings.ActivateBindingContext`), the plain ones. A stick goes to frames taking sticks (`OnGamePadStick`,
  each saying whether it left it unhandled); left to the game, the left stick walks and the right one turns.
- **Input** in the header switches the game's gamepad interface on (the `InputDeviceInterfaceStyle` setting,
  `INPUT_DEVICE_INTERFACE_TRANSITION`), kept between runs: it takes Edit Mode's Gamepad layout (`SetActiveLayout` is
  real now) and its own bars; Start opens the radial menu, the right stick picks in it, the d-pad and A/B work the
  navigation cursor in windows.
- Made right on the way, as the client does them:
  - bindings marked `runOnUp` run again with `keystate` "up" when the key comes up;
  - a click binding clicks a down-registered button on the press (down = true), an up-registered one on the release
    (it clicked once, as an up-click, on the press);
  - a scenario's `key()` is a tap, down and up;
  - script names are case-blind (the game sets `OnGamepadStick`);
  - the game's clock runs securely: a scenario's `wait()` no longer taints every OnUpdate it runs (the gamepad's

- The gamepad mode's own key defaults are the client's own and not in its interface files: the simulator's are the

## 2026-11-21: speed

Measured with `tools/profile-boot.lua` and `tools/profile-runtime.lua` (LuaJIT's sampling profiler).

- **Startup 24 s -> under 4 s.** A third of it was a `cmd /c dir` started for every folder listed, another third
  trying each part of every path with `io.open` (a folder never opens on Windows, so each fell to a listing too).
  Folders are now listed through Windows itself (`FindFirstFileW`, LuaJIT's FFI) and kept for the process;
  `findPath` resolves from the kept listings. The addon that made each region is worked out from a cache of
  functions, once per frame built (no addon code runs during a build), and the walk stops where the simulator loads
  files. The JIT is off and the collector slower during startup (code run once), as usual after it.
- **Each tick 9 -> 5 ms**: `OnSizeChanged` is checked on the frames that have a handler, not every frame there is.
- **Scene request about 20 -> 8 ms**: the drawing order (visibility, strata, level, raised) is kept until something
  changes it (`W.touchOrder`, rebuilt at least every quarter game second); text layouts are kept by text, font and
  width; JSON writes common strings and numbers without patterns or the wrapped `string.format`.
- **The server** passes the scene's JSON through as the simulator wrote it (it was read and written again), and the
  clock runs at 30 ticks a second (was 20).
- **The page** draws only items that changed (every style was set again at every frame), and asks for the next
  frame as soon as it has drawn one (it waited 60 ms between): about 23 frames a second with the map open, 1 ms each
  to draw.
- The scenario suite: over 10 minutes -> 160 s.
- Fixed on the way: the gamepad interface saved on is switched on after everything loaded (set before, an addon
  loading ahead of Blizzard_Gamepad errored).
- A texture's `scale` in XML is kept, as a frame's: the gamepad's gold focus glow (scale 0.5) drew its sliced corners
  at twice their size, overlapping in the middle of a dropdown or round a window.
- A font string with no anchors is drawn over its frame, as a texture is: the gamepad's button legend (top left) showed
  its icons without their labels.
- `useParentLevel` frames are drawn at their parent's level, their layers among the parent's: a tooltip's background
  and border (its NineSlice) were drawn over its text, so every tooltip looked dim.
- Frames clamped to the screen (`SetClampedToScreen`, every tooltip) are kept on it: a tall tooltip near the top ran off
  the screen.
- **LT and RT switch the gamepad's crossbar**: the game asks `IsKeyDown(GetBindingKey("GAMEPADLEFTMOD"))`; the
  simulator's `GetBindingKey` did not look in the gamepad mode's bindings and `IsKeyDown` was a stand-in (always no).
  Both real now (pad buttons, modifiers, keys held on the page).
- **The scene is exported once per tick, for every page** (`server.py` SceneCache): the tick loop exports it while a
  page watches, keeps the JSON, and a page's request returns it at once or waits for the next (no busy polling; a
  second tab or the popped-out controls cost nothing). An input wakes the clock, so its effect shows on the next
  frame. The clock keeps its cadence, the work of a tick counted in. Inputs answered in about 3 ms, 30 frames a
  second while walking.

## play.py: runs never get stuck or left behind

- A single scenario prints as it goes (several still print each report whole as it ends): `lua/play.lua` writes
  unbuffered (Windows' C library takes "line" buffering for full, which held a quiet run's lines until it ended).
- `--time-limit=SECONDS` (default 900): a scenario running longer is ended and counted as failed, with what it
  printed so far.
- On Windows the script's LuaJIT runs end with the script, however it ends, and the script ends when whatever
  started it is stopped: stopping a run no longer leaves LuaJIT working in the background.
